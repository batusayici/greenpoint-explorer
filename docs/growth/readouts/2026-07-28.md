**The pull script's numbers are inflated by about a third, and have been all

|---|---|---|---|

| `192.168.1.157:5195` | 113 | 1 | LAN dev server (phone testing) |
| `localhost:5192` | 101 | 5 | dev |
| `localhost:5194` | 41 | 2 | dev |
| `localhost:5193` | 13 | 2 | dev |
| `localhost:5195` | 6 | 1 | dev |
| `localhost:5196` | 2 | 2 | dev |
| **dev + LAN subtotal** | **276 (34%)** | **13** | not visitors |

Consequences, in order of how much they matter:

1. **Every quantitative table in the merged friends-round readout is inflated.**
   Its headline "19 visitors → 12 opened a card (63%) → 10 took an action (53%)"
   counted dev sessions as visitors. It is a dated record, so I have not edited
   it — but it should not be quoted as a baseline again. Cycle 2 onward uses the
   prod-only figures below.
2. **`$exception` was a false alarm.** All 9 exception events are from
   `localhost:5193` — `ReferenceError: todayOnly is not defined` in
   `CardPanel.jsx`, a dev-time error caught during development, last seen
   2026-07-26. **Zero production exceptions.** L4 is genuinely green; I flagged
   this as a possible prod issue in the notification before splitting by host,
   and it isn't one.
3. This is the **fourth** consecutive measurement-layer defect (Vercel Analytics
   off Jul 15–21 → untagged invite links → blocked egress host → dev traffic in
   prod data). Every one was found at readout time, by hand. That pattern, not
   any single defect, is what Proposal 1 addresses.

**All figures in this readout are prod-only** (`$host =
'greenpoint-explorer.vercel.app'`) unless a row says otherwise.

## Top-3 proposals

**No new experiment proposed this cycle.** The max-3 slots are spoken for by
R1/Q1/Q2 at launch, so proposing a fourth would break growth-engine §6 rule 3.
All three below are measurement/readiness work.

### 1. Filter dev traffic out of the pull, and make the sensor fail loudly

- **Hypothesis:** four consecutive windows have been degraded by a silent
  measurement defect found only when someone went to read the data. The defect is
  never the same twice; the *lateness* is.
- **Smallest test:** two one-line changes to `scripts/posthog-pull.sh` — add
  `AND $host = 'greenpoint-explorer.vercel.app'` to the exclusion clause (with
  the origin becoming a variable at cutover, since it changes to
  `greenpoint.life`), and a `SELECT 1` preflight that exits non-zero naming the
  failure (auth / policy / host) in the run's first minute.
- **Metric:** cycles that reach the readout with a clean, live sensor.
- **Decision rule:** if cycle 2 surfaces a fifth distinct measurement defect,
  stop treating these as one-offs and spend a session hardening the pull end to
  end instead of shipping growth work that week.
- **Kill criteria:** if the preflight ever false-alarms and blocks a good run,
  drop it — a noisy gate is worse than none.
- **Autonomy note:** this is a code change (V2, PR-gated, TDD) and **it is not
  in this PR** — this PR is a readout. It's ~10 minutes; say the word.

### 2. Land every Wave 1 `src` row *before* launch day, not during

- **Hypothesis:** the friends round's attribution is permanently unrecoverable
  because links went out bare. Wave 1 sends R1/Q1/Q2 within 48h of cutover —
  exactly the window where a missing row gets skipped "just this once."
- **Smallest test:** the six rows added in this PR, reviewed now.
- **Metric:** every Wave 1 send's `src` visible in the Channels table within a day
  (already `channel-links.md` pre-send checklist item 3).
- **Decision rule:** any Wave 1 send landing with no `src` → that channel's read
  is void for the window; say so rather than reading noise.
- **Kill criteria:** n/a — kit hygiene, not an experiment.
- ⚠ **Reminder (L1):** these rows carry the `greenpoint-explorer.vercel.app`
  origin. At cutover **every row regenerates on `https://greenpoint.life`**. If
  Wave 1 goes out after the flip, regenerate first, then copy.

### 3. Pin the cutover date so cycle 2 has a pre/post boundary

- **Hypothesis:** pre/post is the only instrument available at this traffic
  (growth-engine §6 rule 2), and it needs a dated line in the sand. Target is
  "~Aug 1–8"; L5 and L7 are still open.
- **Smallest test:** Batu names the intended date at merge; the operator treats
  every metric before it as "pre."
- **Metric:** n/a — a scheduling input.
- **Decision rule:** if it slips past Aug 8, cycle 3 reruns this baseline rather
  than pretending a partial launch started the clock.
- **Kill criteria:** n/a.
- **Timing note:** the first real WRL read lands ~Aug 2 regardless. A cutover on
  or after that date means week-1 growth reads and the first retention read
  arrive together, which is the more useful ordering.

## Appendix — where `TALLY_API_KEY` goes (answering Batu's question)

Three things are needed, and the first two are the ones that bite:

1. **Cloud (for the Tuesday routine):** same place `POSTHOG_READ_KEY` went — the
   routine's environment at claude.ai/code. That makes it available to
   `scripts/tally-pull.mjs`, which reads `process.env` and falls back to
   `.env.local`.
2. **Egress allowlist:** `scripts/tally-pull.mjs` calls **`api.tally.so`**. That
   host will be denied exactly the way `us.posthog.com` was this morning —
   adding the key alone will not be enough. Allowlist it in the same place.
3. **Local:** it already belongs in `.env.local` (gitignored via `.env.*`), which
   is where the checkpoint readout records it. Nothing to change there.

⚠ **One security caveat worth your call before doing step 1.** The script's own
header notes that a Tally key is **user-scoped: it inherits every permission of
the account that created it — there are no read-only scopes as of 2026-07 — so a
leaked key could delete forms and submissions.** `POSTHOG_READ_KEY` is scoped
`query:read` on one project; this key is categorically different. Putting it in
a cloud environment is a wider blast radius than the PostHog key was.

Given that R1's denominator is currently a **2-row list**, the cheapest safe
option is: **don't put it in cloud yet — paste the signup count into the PR when
a readout needs it.** If Tally ships scoped keys, or the list grows enough that
manual pasting is annoying, revisit. Either way it must never gain a `VITE_`
prefix (Vite inlines those into the client bundle). Your call; I've made the
argument, not the decision.

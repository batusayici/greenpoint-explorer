## 🔴 Finding 1 — greenpoint.life has never recorded a single analytics event

Every prod event in the project, all time, carries
`$host = greenpoint-explorer.vercel.app`. Not one event — not one `$pageview`,
not one `?src=verify` — has ever arrived on `greenpoint.life`, including on and
after the 2026-08-02 cutover. A query for any event whose `$current_url`
contains `greenpoint.life` returns **zero rows**.

| Day | `greenpoint-explorer.vercel.app` | `greenpoint.life` |
|---|---|---|
| 2026-07-31 | 4 events · 2 people | — |
| 2026-08-01 | 10 · 4 | — |
| 2026-08-02 *(cutover day)* | 59 · 4 | — |
| 2026-08-03 | 7 · 2 | — |

**The most likely explanation is innocent: nobody has visited the new origin
yet.** Nothing has been sent on it, and the cutover was verified with `curl`,
which runs no JavaScript and therefore fires no analytics. I checked the one
code-level cause I could rule out from here — `posthogTransport.js` does no
host-gating and `main.jsx` initializes unconditionally, so there is no reason in
our own code for the new origin to be silent.

**But it is unverified, and it is unverified in exactly the direction that
matters.** Launch-plan §2 step 5 lists "Visit with `?src=verify` → event lands
in PostHog with `src` intact on the new domain" as a cutover verification step;
the data shows no `verify` event on any host since 2026-07-30 (and that one was
`localhost:5196`). That step left no trace, so it either didn't run or ran
without JS. Meanwhile **every row in `channel-links.md` was regenerated onto
`greenpoint.life` in the same commit** — so every Wave 1 link points at an
origin from which we have never received a measurement.

I could not close this from the cloud runner: `curl https://greenpoint.life/`
returns `CONNECT tunnel failed, response 403` — the environment's egress policy
does not cover that host, the same class of block that hit `us.posthog.com` on
7/28. Per the kit rules I am reporting the blocked host rather than routing
around it.

**Recommendation (Batu's call): a 60-second check before any Wave 1 send.**
Open `https://greenpoint.life/?src=verify` in a normal browser, tap one card,
then confirm the event appears with `$host = greenpoint.life` and `src=verify`
intact. If it doesn't, Wave 1 lands unmeasured — which is precisely the failure
that made the entire friends round unattributable, repeated on the sends that
matter most. Adding `greenpoint.life` to the routine's egress allowlist would
let the operator check this itself in future cycles.

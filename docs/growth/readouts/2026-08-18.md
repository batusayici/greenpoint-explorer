## 🔴 Finding 1 — the send gate fires a false do-not-send, on send morning

`npm run preflight:send`, run today at HEAD:

```
  ✗ prod sitemap 152 urls vs local deck 158 (drift -6)
  ✗ NOT CLEAR TO SEND — 1 problem(s):
    · prod sitemap drift -6 — is main deployed?
```

**Main is deployed.** Verified three independent ways before writing this:

| Check | Result |
|---|---|
| Both cards added by today's 13:31 UTC run, fetched on prod | `/e/mccarren-movies-guardians-2-0826` → **200** · `/e/mcgolrick-movies-eternal-sunshine-0829` → **200** |
| Cards on prod's sitemap but gone from the local deck (the stale-deploy signature) | **0** |
| Prod `/e/` url count vs local **live** card count | **149 vs 149 — exact** |

**Root cause, from the code, not inferred.** The check compares two things that
were never the same quantity:

- `scripts/send-preflight.mjs:102` — `const drift = locs - report.deckSize`,
  tolerance `Math.abs(drift) <= 5`.
- `report.deckSize` is `cards.length` (`src/demand-test/sendPreflight.js:125`) —
  **every card in `cards.json`**.
- The sitemap renders `liveCards(cards, now)` plus three fixed urls
  (`src/demand-test/aeo.js:508–513`), and `liveCards` is `!isExpiredCard`.
- `isExpiredCard` retires a **news** card 30 days after publication
  (`NEWS_SHELF_LIFE_DAYS = 30`, `filterCards.js`) — and the deliberate rule one
  comment line above it is *"Undateable news is never deleted — we don't delete
  what we can't judge."*

So aged-out news cards stay in `cards.json` forever and leave the sitemap on
day 31. Today there are **nine** of them — `rockaway-rocket`,
`archestratus-closed`, `mcguinness-redesign`, `meeker-plume-monitoring`,
`green-st-condos`, `monitor-point-approved`, `saint-vitus-bushwick-move`,
`light-up-mccarren`, `vault-gallery-culture-house`. Nine expired news cards + 3
fixed urls = the observed −6, exactly.

**This is a drift that only grows.** Every news card the ingest ships crosses
day 31 eventually, and none are ever removed. The check passed on 8/13
(sitemap 161 vs deck 159) because fewer news cards had aged out; it will now
fail on every send until it is fixed or the news backlog is pruned — and it
fails *loudest* on the morning of a send, which is the only morning anyone runs
it.

**The patch is one line** (`scripts/send-preflight.mjs:102`) — compare against
what the sitemap actually renders:

```js
// drift = locs - report.deckSize
const drift = locs - (report.liveDeckSize + 3); // sitemap = liveCards + /, /terms, /privacy
```

…with `liveDeckSize: liveCards(cards, now).length` added next to `deckSize` in
`assessSend`, and a test for the "expired news card lingers in the deck" case.
**I have not shipped it.** Code is human-gated (CLAUDE.md) and this PR's remit
is the readout; the patch is quoted so it is a five-minute change rather than a
rediscovery. See Proposal 1.

**What this means for today's send, stated plainly:** the two org notes are
clear to go on the evidence above — all five `src` links resolve 200 with the
query intact, the counts below were regenerated at 09:xx ET today, and prod is
serving the exact deck those counts describe. **The failure is in the
instrument, not the send.** But that judgment is mine, and the tool that is
supposed to make it is currently saying the opposite — which is precisely the
situation the tool was built to prevent (2026-08-13). Batu should decide
whether to patch first or send on the manual clearance.

## 🟡 Finding 3 — the demand gate's denominator, derived for the first time

D1 (ratified 2026-08-17, pre-Wave-1-data) made the PMF demand gate a rate:

> *of locals who visit twice, **≥25% return in ≥3 of any 4 consecutive weeks,
> floor 12 people***, with **≥30 weekly returning locals** retained as the
> business-viability line.

`gtm-state.json` recorded the gap honestly — *"Rate denominator not yet
derived — Tuesday's readout adds it."* Derived here, mechanically, from the
production pull:

| Component | Value | How |
|---|---|---|
| Locals with **≥2 distinct visit days** (the denominator) | **16** | NYC-metro geoip, `uniq(toDate(timestamp)) ≥ 2` |
| Of those, active in **≥3 distinct weeks** (the numerator) | **3** | 2 people in 3 weeks · 1 person in 4 weeks |
| **Gate rate** | **3 of 16 = 19%** | against **≥25%** |
| **Floor** | **3** | against **≥12 people** |
| **WRL proxy** (viability line) | **4 people**, 7 events (3 at `weekIndex 1`, 1 at `weekIndex 2`) | against **≥30** — distance **−26** |

**Both parts of the gate are unmet, and that is the expected reading, not a
signal.** The data window is 2026-07-21 → 2026-08-18 — **4.3 weeks** — so "≥3
of any 4 consecutive weeks" has barely had room to be true for anybody, and
Wave 1's first cohort arrived five days ago. The gate reads **~Sep 15
provisional** and **~late Oct firm**, and carries the P1 contamination label
and the P8 peak-cohort label when it does. Quoted now so the series has a
first point and so the derivation is written down before it matters.

**Two caveats on the derivation, both mine to flag:**

- "Locals" is geoip city, and PostHog is cookieless — a person who clears
  storage or switches device becomes a new `distinct_id`, which pushes this
  rate **down**, never up. Same asymmetry P1 already names for Q2's webview
  traffic.
- "≥3 distinct weeks" is computed over *all* weeks, not a sliding 4-week
  window. At 4.3 weeks of data the two are nearly identical; from mid-September
  they diverge, and the query needs the window before then. See Proposal 2.

**The WRL proxy doubled, 2 → 4 people**, and it remains structurally immune to
the automated traffic (a stateless fetcher cannot carry `localStorage` across a
week). All four are real returners.
